详解 2
术语的完整定义与两侧最小结构
空链表与单节点的链是两类边界情形，定义里必须交代清楚：空链表没有有效节点、head 为
空；单节点链的 head 同时是头节点与尾节点，它的指针域为空。常见的操作错误大多出现
在这两个边界上。
最小结构的两侧写法（摘自实跑的 examples/array_vs_list_cost.c 与 examples/array_vs_list_cost.jl，为
便于阅读，摘录里的注释比脚本中的略多）：
typedef struct Node {
int data; /* 数据域 */
struct Node *next; /* 指针域：指向下一个节点，尾节点与空链表为 NULL */
} Node;
Node *head = NULL; /* 空链表：head 是空指针 */
mutable struct Node
data::Int
next::Union{Node,Nothing} # 要么指向下一个节点，要么是 nothing
end
head::Union{Node,Nothing} = nothing # 空链表：head 是 nothing
两侧的写法差别不在语法，而在“空”由谁保证。C 侧的 next 是一个地址，空值写成 NULL，“这
里没有下一个节点”这件事只存在于程序员的约定里，编译器不会替程序检查；Julia 侧把“可
能为空”写进字段类型 Union{Node,Nothing}，读 next 之前必须先判断它是不是 nothing，否则会抛
MethodError。要表达的是同一件事，一处靠约定，一处靠类型。

由此可以解释数组与链表在访问上的差别从何而来：数组的元素地址等于首地址加下标乘

详解 4
对照表行内术语的解释与实跑全表
表中术语按本课的解释口径：连续内存空间指首地址与长度都确定的一段地址区间，元素
按下标依次排布，第 𝑖 个元素的地址由首地址加偏移量算出。分散内存空间指各节点单独申
请、地址互不相邻，节点之间的次序由指针给出。容量扩展指在已有元素之外再容纳更多元
素的能力：长度不可变的数组只能重新申请并复制，可灵活扩展的链表只需再挂一个节点。
内存效率指存下同样多的元素各需要多少字节，数组除了元素本身没有额外开销，但为扩容
预留的空闲位置可能长期闲置；链表的每个节点都要多付一个指针域，没有闲置预留。

详解 5
判据的推演与课后作业的对应
场景一里，一组数据被反复按下标读取与整体扫描，且规模在开始前已知：这类负载的代价
几乎全在“定位到某个位置”，数组把定位变成一次地址计算，链表每一次定位都要顺着指针
走。场景二把同一份功能换到链表上，正好把这条差异量出来：插入变便宜、定位变贵。场
景三里，写入的位置固定在链的一端、位数事先不可知、每个新元素都是刚算出来的，链表
的三条长处（分散分配、按需增长、改指针不搬元素）全部对上，而它的短处（定位慢）在“只
在头部操作”的用法下不出现。
把三个场景的差别归拢，能变的东西只有两件：怎么读（访问模式）与怎么写（更新模式与
规模是否变化）。这就是两条判据轴的来源。
与课后作业的对应：作业里那道要求从存储结构、内存分配、访问时间的步骤、插入与删除
的步骤四个方面比较链表与一维数组的题，就是上面判据的书面形式。答的时候四个方面要
各带前提与数字，否则四条结论会互相矛盾：只说“链表插入是 𝑂(1)”而不提“已持有前驱指
针”，与只说“数组访问是 𝑂(1)”而不提“下标已知”，是把同一个错误犯了两次。

Node *nodeAt(Node *head, int idx) {
Node *p = head;
int i = 0;
while (p != NULL) {
g_steps++; // 看过的节点数
if (i == idx) {
return p;

p = p->next;
i++;

function node_at(head::Union{Node,Nothing}, idx::Int)
p = head
i = 0
while p !== nothing
steps[] += 1
i == idx && return p
p = p.next
i += 1
end
return nothing
end
# 按值查找，返回下标，找不到返回 -1
function find_value(head::Union{Node,Nothing}, target::Int)
p = head
i = 0
while p !== nothing
steps[] += 1
p.data == target && return i
p = p.next
i += 1
end
return -1
end

void pushBackO1(Node **head, Node **tail, int data) {
Node *p = createNode(data);
if (*tail == NULL) { // 空链表：head 与 tail 同时为空

删除的边界与 C 侧释放
四条边界要在写删除函数时逐条想到：
1.空链表：什么都不做，直接返回，不要先解引用 head。
2.被删节点是头节点：没有前驱，要改的是 head 本身，形参需要用二重指针或哨兵节点。
3.被删节点是尾节点：改完之后尾节点的 next 仍然要保证是空值，否则遍历会走出链表之外。
4.链表中没有这个值：走完整条链，什么都不改。
C 侧的两条内存纪律：
释放的时机在改完指针之后。先释放再读 victim->next 是读已经还给系统的内存（见下一小节
的反例）。
删除只释放被删的那一个节点，不要顺手把 victim 的后继也释放掉。后继还要留在链表里。
Julia 侧没有 free：victim 一旦不再被任何变量引用，垃圾回收就会收回它，所以代码里只留

逻辑在两种语言里是同一套。

详解 13
三个问题的思路、完整源码与实跑输出
第一问：头节点的作用不是“第一个数据节点”，而是把头节点与中间节点在程序结构上拉
平。不带哑节点时，“删除头节点”要改的是调用者手里的那个 head，而“删除中间节点”改的
是别人的 next，两件事写法不同，函数体里就必然出现特判（后面删除那两节会看到这个特
判长什么样）。哑节点的数据域可以放任意无害的东西，常见选择是放链表长度、放 0、或
者干脆不初始化也不读它；本课示例放 0，并且说明打印时它会出现。
第二问：Node 变量如果声明在函数内，它的生命周期随函数返回而结束，函数返回后那块栈
空间随时会被别的调用覆盖。createNode 要把一个节点交给调用者长期使用，就必须让它的生
命周期长于函数调用，这只能靠堆：malloc 申请的内存只有显式 free 才归还。
第三问：返回指针而不是返回结构体，有两层理由。一是语义：链表的节点本来就要靠地址
互相引用，返回的是“某个节点的身份”，不是“一份节点副本”；如果返回 Node 值，调用者拿
到的是栈上的一份拷贝，接不上链。二是代价：Node 值返回要整块复制，指针返回只复制一
个地址。
命名混用的后果：不同资料里节点定义有 struct node、typedef struct Node、typedef struct ListNode
（字段名 data 或 val）等写法，类型名与字段名都不一致。混用可以直接实验出后果：在同一
个文件里用其中一套定义节点、用另一套写函数原型，clang 会报 incompatible pointer type。本
课统一用上面那个 typedef 写法。

详解 15
哨兵法与递归法中那几行到底在做什么
哨兵法：current 从 &dummy 出发，并且总是站在待检查节点的前一个位置（循环条件写成 current-
>next != NULL），这是这份代码能只用一层指针的原因；如果让它直接站在待判节点上，就要
再引入一个 prev，写法就退回双指针法。dummy 只在函数体内存在，函数返回就“撤销”。
递归法：head->next = deleteNodesRecursive(head->next, key) 这一句的含义是“把删干净之后的子链表
的头接回来”，因此返回值的类型必须是节点指针。头节点改变与接回新头是同一个返回值
完成的，这也是它不需要二重指针的全部原因。

详解 17
三份代码的六维对照
（n 为链表长度，栈上的哑节点不计入堆内存）
删头是否需要特判：双指针法需要（prev == NULL 支路）；哨兵法不需要；递归法不需要（返回
值即新头）。
形参形状：双指针法 Node**；哨兵法 Node* 但要接收返回值；递归法 Node* 且接收返回值。
堆内存增量：三者都是 0；哨兵法的哑节点在栈上。
额外附加空间：双指针法与哨兵法 O(1)；递归法 O(n) 栈帧。
每节点常数代价：双指针法最小；哨兵法与之相当（多一次 current->next->data 的间接访问）；
递归法最大（函数调用 + 返回）。
出错风险点：双指针法是 free 与推进后继的顺序、以及二重指针的层次；哨兵法是把返回值
漏赋回 head、以及误把哑节点当作数据节点；递归法是忘记基准情形、以及长链表栈溢出。

详解 29
展开：平行更新与顺序更新的差别
正文定的那条口径（目标格点在步首为空才算成功、同格点冲突则都不动）属于两类合法判
定时机中的平行更新一类。“每一步对所有粒子各尝试一次跳跃”只规定了尝试的次数，没有
规定判定的时机，而两种时机给出两个不同的模型：
平行更新（正文口径）：所有粒子的判定都基于这一大步开始时的状态，判定完成之后才统
一落地。它的好处是可复现性好（落地顺序不影响结果）、便于并行；代价是要处理两个粒子
选中同一个空格点的情形，规则必须写明（正文取“都不动”）。另一种常见的平行更新口径
允许粒子驶入“在本步被腾空”的格点，那是交通流里跟车效应（前车刚走，后车立刻跟进）
的模型，两条口径给出的密度与流量不同，不能混用。
顺序更新：一个粒子一个粒子地判定与落地，判定基于当时最新的状态。它的好处是规则里
没有冲突这一类情形，坏处是落地顺序会影响结果，因此必须规定顺序（通常取随机顺序），
否则统计量会依赖格点的排列。
同一个种子、同一组参数下，两条口径的累计跳跃次数会明显不同，这正是“口径不写清就
不可对照”的意思。核对时要盯住的一件事是冲突计数：本节口径下 𝜌=0.8 的 5000 步里出
现了 8645 处冲突（每处两个粒子），若实测长期为零，两种可能，一种是密度太低（𝜌 的取
值偏低时空格点多，两个方向抢同一个空格点的机会自然减少），另一种是后退这一路没有
接上（向后尝试根本没有登记到目标格点），后一种是实现错误。

调用栈机制、C 侧两版代码与三处容易走偏
调用栈机制：函数被调用时运行时在调用栈上分配一层栈帧，放局部变量、参数与返回位置；
返回时这一层被移除，控制权回到上一层。递归函数“递”阶段逐层压入，深度是同时存在的
未返回调用个数；触发基线后“归”阶段逐层弹出。所以递归的附加空间等于深度乘每层栈帧
大小，而不是等于总调用次数。归并排序按分解树数出的调用次数是 2𝑛−1（𝑛=4096 时
8191 次），深度只有 13 层，两者相差两个数量级以上。
尾递归（tail recursion）指递归调用发生在返回前的最后一个动作：返回上层后不必再做别
的事，上一层无需保存上下文，编译器可把这次调用改写成一次跳转，空间与循环相当。不
是尾递归的递归（例如本讲递归删除，它在返回前还要把子链表的头接回来）得不到这条优
待，深度是实打实的。
C 侧两版代码见 examples/appendix-dc-rec-vs-loop.c（sortRec 与 sortIter，与 Julia 两版逐行对应）。
三处容易走偏：
把“循环”理解成“没有栈”：循环版自己也得记账，只是账记在变量与临时数组上，不记在调
用栈上；换了写法的代价并没有消失，只是换了地方。
以为递归的附加空间等于调用次数：见上，等于深度乘栈帧。
把尾递归优化当成语言保证：两侧实测给出两种结果，代码的正确性不能建立在这条优化是
否发生之上。
